# ADR-0006: localization の乖離は角度ではなく変化率で見る

- 状態: 採択
- 日付: 2026-09-11
- Phase: 5

## 背景

`cr2-base.yaml` の `derived_telemetry` に、Phase 0 の時点でこう宣言してあった:

```yaml
- name: yaw_vs_ndt
  description: IMU の yaw と scan-to-map localizer の yaw の差。
    localization 劣化（TF 凍結 → Nav2 abort）の早期検知に使う。
    実機で最も再発している故障モード。
  inputs: [/imu/data_rep145, /pcl_pose]
  unit: deg
  warn: 10.0
  crit: 25.0
```

issue #40 では実装前に「IMU の yaw と localizer の yaw は基準が違う。生の差を
使うのか、オフセットを除くのか、起動時の差を基準にするのかを決めること」を
条件にしていた。**推測せずに実データで確かめた。**

## 測ったこと

代表 bag（`bags/2026-07-31-campus`、235 s、localization は健全）。

### 1. IMU は姿勢を推定していない

```
/imu/data_rep145  n = 23509
  orientation_covariance[0] : すべて -1.0
  q.x / q.y / q.z / q.w     : 幅 0.000000（単位四元数のまま）
  yaw                       : min 0.000  max 0.000  幅 0.000 deg
  angular_velocity.z        : -0.569 .. +0.580 rad/s（|積分| は約 900 deg 相当）
```

`sensor_msgs/Imu` の規約で `orientation_covariance[0] < 0` は「姿勢は未推定」。
**比べるべき「IMU の yaw」は存在しない。** 既存スタックの EKF も同じ理由で
orientation を skip している（`whill_localization/config/ekf_odom.yaml` の注記 (3):
「yaw 推定は angular_velocity_z の積分に一任する」）。

角速度のほうは健全に出ている。

### 2. 角度で比べると誤検知になる

姿勢が無いと分かる前に、角度どうしの比較を実装して bag に通してあった。
オフセットを実行時に推定し、旋回中は評価を止める作りにしても:

```
乖離 deg: 中央 1.83  95% 37.01  最大 50.53
warn (>=10 deg): 10.1 %   crit (>=25 deg): 18.2 %
crit の区間: 164-166s, 171-182s, 192-194s, 207-235s
```

**localization は健全なのに 28 % の標本で warn 以上。** 進行方向を第三の証人に
すると、localizer の yaw は前半・後半とも進行方向に対して -2 〜 -4 度で
安定していた（後半の標準偏差 6.5 度）。ずれていたのは IMU 側であり、しかも
その正体は「姿勢を出していないので単位四元数が置かれている」だった。

### 3. 変化率で比べると綺麗に分かれる

ジャイロの `angular_velocity.z` と `/pcl_pose` の yaw 変化率を 1 秒窓で比較:

```
回帰係数（原点通し）  0.9855      ← 符号もスケールも一致
|乖離| deg/s          中央 0.11  95% 1.08  99% 1.65  最大 3.06
  うち旋回中          中央 0.58  95% 1.36  最大 1.85
```

同じ bag の t=155 s から **TF 凍結を模擬**（pose の yaw を止める）と:

```
|乖離| deg/s   中央 4.70  最大 26.96
warn 49 %  crit 35 %
凍結（t=155.0s）から最初に crit になるまで 2.8 s
```

健全時の最大 3.06 と、故障時に出る 15 前後のあいだは十分に空いている。

## 決定

**`yaw_vs_ndt`（角度、deg、warn 10 / crit 25）を
`yaw_rate_vs_ndt`（変化率、deg/s、warn 5 / crit 10）に置き換える。**

閾値は上の実測から決めた。健全時の最大 3.06 deg/s の上、故障時の 15 deg/s の下。

変化率にすると副次的に次が要らなくなる:

- **オフセットの推定が要らない。** 角度どうしだと IMU と map で yaw の基準が
  違い、差は約 180 度になる。実行時推定しか手が無く、しかも「起動時点で既に
  ずれていたら、そのずれが基準になる」という穴が残る
- **積み上がった誤差に汚されない。** 変化率は各窓で独立
- **見たい故障を直接見る。** TF 凍結は「localizer の yaw が動かない」ことなので、
  変化率の食い違いそのもの

あわせて `rt_9axis` の telemetry から `yaw`（`__yaw_deg`）を落とし、
`yaw_rate`（`__yaw_rate_deg`）にした。**姿勢を出さないドライバに `__yaw_deg` を
宣言すると「常に yaw 0 度」を正しい値として画面に出すことになる。** #39 で
実際にそうなっていた（live スクリーンショットに「↑ 0 deg」と出ていた）。
`extract()` は `orientation_covariance[0] < 0` を見て None を返すようにした。

車体の向きは localizer の pose から出る（俯瞰図が既に描いている）。

## 帰結

**得たもの**

- 健全な代表 bag 235 s を通して **warn / crit ゼロ**。誤検知を出す指標は
  そのうち誰も見なくなるので、これが一番大事
- TF 凍結の模擬で 2.8 s 以内に crit
- 閾値に実測の根拠がある。推定値のままの他の閾値（温度・電力）と違い、
  ここは「なぜ 5 と 10 か」を数字で言える

**払ったもの**

- **回っていないときは何も言えない。** 止まっていれば両方 0 なので、localizer が
  凍結していても乖離は出ない。**「乖離が小さい = localization が正しい」ではない。**
  宣言の description と UI の説明にこれを書いてある
- 絶対的な向きのずれ（じわじわ回転がずれる類）は見えない。変化率が一致したまま
  角度がずれることはありうる。これは `/alignment_status` の fitness（配車パネル）と、
  地図に重ねた LiDAR の見え方で見る

## 覆すべき条件

- **姿勢を推定する IMU に載せ替えたとき。** `orientation_covariance[0]` が正に
  なったら、角度どうしの比較を足す価値が出る（変化率と併用する。置き換えない）
- 実機で「変化率は合っているのに位置がずれている」故障が観測されたとき

## 実機検証待ち

- 実機の localization 劣化時にこの指標が先に動くか。閾値 5 / 10 deg/s は
  **1 本の bag から決めた**もので、路面や速度域が違えば健全時の分布も変わりうる
- 屋外の長距離走行での健全時の分布
